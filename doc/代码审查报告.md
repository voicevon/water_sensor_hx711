# 代码审查报告

日期：2026-09-21　范围：`src/` 全部源文件（10 个 .cpp/.h + Web 页面）
方式：主审初筛 + 2 个独立验证代理复核，5 项问题全部确认（2/2 或 1.5/2 一致）

## 总体结论

架构分层清晰，MQTT 多任务加锁、NVS 参数版本管理、两步转换公式实现均正确。无架构性问题，1 项需修复的真实 Bug，4 项健壮性/可维护性小问题。

## 问题清单

### 问题 1（Major）：MQTT 域名悬垂指针

- 位置：`src/wifi_mqtt.cpp` L142、L216
- 分析：`PubSubClient::setServer(const char* domain, ...)` 只保存指针不拷贝（库源码 PubSubClient.cpp L715-719：`this->domain = domain;`）。而
  - L142：`setServer(get_mqtt_broker().c_str(), ...)` 传入临时 String，语句结束即析构；
  - L216：`setServer(broker.c_str(), port)` 传入 `wifi_mqtt_init()` 局部 String，函数返回后失效。
- 触发路径：DNS 解析失败 → 走域名分支 → 后台任务 `s_mqttClient.connect()` 使用悬垂指针 → 未定义行为（可能连接失败、崩溃或连到错误地址）。DNS 成功走 IP 分支（按值复制）不受影响。
- 建议：新增 `static String s_broker_domain;` 保存域名副本，两处均传副本的 `c_str()`。

### 问题 2（Minor）：读取超时回退值初始为 0

- 位置：`src/HX711Sensor.cpp` L19、L89-92
- 分析：`s_last_u16[3] = {0,0,0}`。在线通道首次读取成功前若超时，输出 0，BLE/MQTT/Web 均收到"像真实读数的 0"，订阅端无法区分离线/异常与真实值（正常空载约 32768 附近）。
- 建议：初始值改为名义基线 32768。

### 问题 3（Minor，需设计确认）：看门狗仅覆盖 DYNAMIC 算法

- 位置：`src/Sensor.cpp` L127-143（_runDynamic 内）
- 分析：5 小时有水强制复位看门狗只在 DYNAMIC 算法实现；DISCRETE（L176 起）与 ENVELOPE（L231 起）无此机制。若采用这两种算法且卡死在 HAS_WATER，无超时退出。
- 建议：若需三算法一致，将看门狗上移到 `pushRaw()` 公共层；若 Python 原版即如此，可保持现状。

### 问题 4（Minor）：参数同步代码重复

- 位置：`src/main.cpp` L69-76 与 L139-146
- 分析：setup() 与 loop() 各有一段逐行相同的 8 行 NVS→Sensor 参数同步代码。
- 建议：提取 `static void apply_nvs_params(int i);` 消除重复。

### 问题 5（Minor）：API 的 n 参数无数字格式校验

- 位置：`src/web_config.cpp` L179-192（handle_post_hx711）
- 分析：`s_server.arg("n").toInt()` 对非数字输入（如 `?n=abc`）返回 0，而 0 是 N 的合法值，垃圾输入会被当作 N=0 写入 NVS 并触发阈值重置。前端 JS 已有 0~8 校验，API 层无。
- 建议：写入前校验字符串全为数字，否则返回 400。

## 修复优先级建议

2. 问题 2、4、5 低成本顺手修
3. 问题 3 需先确认设计意图再决定
